# FlameDelta

**Find which JavaScript functions got hotter between two CPU profiles.**

[Try the live comparison](https://brohum10.github.io/flamedelta/) · [Inspect the synthetic profiles](examples/) · [Tests](https://github.com/brohum10/flamedelta/actions/workflows/tests.yml)

FlameDelta reads two Chrome/Node V8 `.cpuprofile` files locally in the browser. It ranks source locations by the change in their share of sampled function time, shows both recordings side by side, and exports the comparison as CSV. It does not send the files to a server. A constructed catalog-page example loads on first visit, so the site can be explored without a profile on hand.

## What the demo shows

The checked-in example contains **200 samples per profile**, at 5 ms per sample. In this deliberately constructed case, `renderCards` moves from **22.2%** of baseline sampled function time to **38.6%** of candidate sampled function time, a **16.4 percentage-point increase**. Absolute attributed sample time moves from 200 to 340 ms. This is a teaching fixture, not a benchmark of a real site or an improvement made by this tool. The input profiles and computed [evidence](examples/demo-evidence.json) are committed so the numbers can be checked.

## Try it

Open the [live demo](https://brohum10.github.io/flamedelta/) and replace either example profile with your own `.cpuprofile` file. The other side remains in place until you replace it too. Use **Restore demo data** to reset. The search field filters the comparison table, and **Export CSV** downloads the current result.

To run locally, serve the repository root over HTTP (ES modules and example-file fetches do not work reliably from a `file://` URL):

```sh
python3 -m http.server 8000
```

Then open `http://localhost:8000`. There is no package installation or API key. Node.js 20+ is needed only to run the automated checks:

```sh
npm test
npm run examples
```

For a Node program, the documented `node --cpu-prof your-script.js` flag writes a `.cpuprofile` when the process exits. Record a comparable workload for the baseline and candidate. [Node CLI documentation](https://nodejs.org/api/cli.html#--cpu-prof)

## How the comparison works

1. Parse `nodes`, `samples`, and `timeDeltas` from the [DevTools Profiler profile format](https://chromedevtools.github.io/devtools-protocol/tot/Profiler/#type-Profile). Each sample identifies the top stack frame; each delta is a microsecond interval. The reader checks IDs, references, tree connectivity, sample counts, and nonnegative safe-integer intervals before using the data.
2. Attribute each sample interval to its top frame (**exclusive sampled time**). Group frames by function name, URL, zero-based line, and column. Common profiler pseudo-frames such as `(idle)`, `(program)`, `(root)`, and `(garbage collector)` are excluded from the function-time denominator, while their combined share is shown separately.
3. Divide each frame's attributed time by the recording's total sampled function time. Subtract the baseline share from the candidate share and rank by percentage-point increase. This normalization helps compare recordings of different lengths; absolute sample milliseconds remain visible for context.

The implementation is a dependency-free ES module in [`src/profile.js`](src/profile.js). The browser UI uses text nodes for imported names and source paths. Files over 15 MB are rejected before parsing. The synthetic fixtures are generated by [`scripts/build-examples.js`](scripts/build-examples.js), and CI checks that regeneration does not change committed evidence.

## What the ranking cannot prove

- A higher share does **not** prove a release is slower. The candidate could have less total work, and sampling noise, different inputs, warmup, runtime versions, or source line shifts can change ranks.
- The displayed milliseconds are **sample interval estimates**, not exact wall-clock timings, total CPU utilization, or causal attribution. Compare repeat recordings and a controlled workload before acting.
- Source-location matching is intentionally strict. A moved line may appear as one removed and one new frame. Source maps, multi-process aggregation, call-tree visualization, and profile formats without `samples` and `timeDeltas` are outside this version.
- The browser limit is 15 MB per file. Larger profiles need a streaming or server-side parser; the current tool does not silently truncate them.
